Platform blueprintv1.0

Idea-as-a-Service

An AI-native software factory that takes a product idea (ERP, web, mobile, IoT, network, cyber) from planning to deployment and maintenance, using local LLMs, type-safe AI, an AI harness and agents, under a proper SDLC.

Contents: vision and scope, architecture (7 diagrams), SDLC with gates, type-safe AI, local models, hardware and software requirements, ERP worked example, maintenance, security and compliance, team and cost, roadmap, risks, 30-day checklist.

All costs, throughputs and timelines are planning estimates (2026 prices) to be validated by benchmarking. Model names date quickly; the architecture does not depend on any single model.

1. Executive summary

You asked for an "IaaS" that builds products for people who have no engineering team. I have read this as Idea-as-a-Service: a client brings an idea and receives a running, maintained product. If you meant Infrastructure-as-a-Service, sections 13-14 (hardware, software) and the deployment diagram still apply.

Core design decision. Do not build "one big agent". Build a deterministic control plane (workflow engine, policy gates, typed artifact registry) that employs role-specialised agents, each wrapped in an AI harness that forces typed outputs, runs code only inside sandboxes, and accepts work only when independent verifiers (compilers, type-checkers, tests, scanners) pass. Local open-weight models supply the intelligence; humans sign off at a small number of high-risk gates.

What the platform delivers

  • Planning: an interviewing agent turns an idea into a PRD, acceptance criteria, a fixed-scope quote and a risk register.
  • Development: architecture and typed contracts first, then tests, then code, in small reviewed pull requests built inside sandboxes.
  • Deployment: infrastructure-as-code, signed images, SBOM, canary release, one-click rollback, into the client's cloud or yours.
  • Maintenance: monitoring, ticket triage, ticket-to-patch loop, dependency and security patching, monthly releases, SLOs.
  • Domains: web/ERP/SaaS first; then mobile, cyber-security products, network automation, IoT/embedded, each with its own tool-and-test squad.

Honest expectations

  • Agents reliably produce CRUD-heavy business software on mature frameworks. Novel algorithms, deep hardware timing, regulated logic (tax, payroll, medical) still need human experts. The design makes those expert touchpoints explicit and cheap instead of pretending they vanish.
  • Autonomy is a dial per project and per domain. Start supervised (human approves every merge); raise autonomy only where your own eval results prove it (e.g. 90%+ of golden tasks pass unattended).
  • For ERP, start from an open-source core (ERPNext or Odoo Community) and customise, instead of generating accounting logic from scratch.
  • Cyber and network work touching live systems is authorised, scoped and gated; offensive tooling runs only in an isolated range against targets the client owns.

Recommended path

Rent an 8-GPU node for 4-8 weeks, benchmark open models on your own task set, build the harness + web/ERP squad, ship one pilot ERP with human gates, then expand domain by domain (roadmap in section 18).

Design principles

  • Contracts before code. Every hand-off is a typed artifact (JSON-schema, OpenAPI, protobuf, SQL DDL, IaC), so agents cannot drift.
  • The model proposes, deterministic code disposes. No LLM approves its own work; compilers, tests and policy engines do.
  • Tests first. Acceptance criteria become executable tests before implementation starts.
  • Least privilege + isolation. Generated code and agent tools run in microVM sandboxes with no default network egress.
  • Local first. Client data and code never leave your infrastructure unless the client opts in to a hosted model.
  • Everything is traced and replayable. Every prompt, tool call and verdict is logged; every failure becomes a regression eval.
  • Client owns the output. Code lives in the client's repo, standard stack, no lock-in to your platform to keep running.

9. Type-safe AI: six layers of defence

"Type-safe" here means an LLM output is never trusted as free text. Each layer removes a class of failure; together they push error rates down to what tests and reviewers can catch.

LayerMechanismTools (recommended / alternatives)Failure it prevents
1 Constrained decodingCompile JSON-schema / grammar to a token mask so invalid output is impossibleXGrammar, Outlines, llguidance built into vLLM/SGLang; llama.cpp GBNFMalformed JSON, wrong enum, missing fields
2 Schema-first agent I/OEvery agent input/output is a versioned schema; validated at the gatewayPydantic v2 / Zod, JSON Schema, BAML, InstructorContract drift between agents
3 Contract-first product codeOpenAPI / protobuf / SQL DDL produced by Architect, code generated against itopenapi-generator, buf, Prisma/SQLAlchemy, tRPCAPI mismatch between frontend, backend, mobile
4 Typed target languagesPrefer TypeScript strict, Rust, Go, Python + mypy/pyright strict; type-check in the looptsc, mypy/pyright, cargo check, clippyWhole class of runtime errors
5 Syntactic + structural gatesTree-sitter parse, lint, formatter, forbidden-API rulesTree-sitter, ESLint, Ruff, Semgrep custom rulesBroken syntax, banned patterns, secrets in code
6 Behavioural verificationTests written first, plus property tests, mutation tests, golden datasetspytest, Jest, Hypothesis/fast-check, Stryker/mutmut, PlaywrightLogic errors types cannot see
Limit: types and schemas guarantee shape, not truth. A perfectly typed tax calculation can still be wrong. That is why acceptance tests, property tests and expert sign-off exist for business-critical logic.

15. Maintenance and operations

  • Monitoring: SLIs/SLOs per product (availability, latency, error rate, data freshness); alerts routed to the SRE agent, then human on-call by severity.
  • Ticket-to-patch loop: support agent classifies and reproduces a ticket, writes a failing test, dev agent fixes, verifiers run, canary release. Bugs become regression tests permanently.
  • Routine upkeep: weekly dependency + CVE updates as automated PRs, monthly release train, quarterly disaster-recovery restore drill, annual pen-test by an external human firm.
  • Incidents: runbooks as code; auto-remediation only inside blast-radius limits (restart, scale, rollback); blameless postmortems generate new tests and runbook edits.
  • Platform self-maintenance: nightly model/prompt eval, drift alarms, prompt and model versioning, canary of new model versions on shadow traffic before promotion.
  • Commercial model: build fee (fixed scope) + monthly plan (hosting, monitoring, N change requests, SLA tiers).

20. First 30 days checklist

  • Week 1: Decide product framing (Idea-as-a-Service), pick the ERP vertical and one pilot client/use-case; set up Git, CI, Vault, observability skeleton; rent an 8-GPU node.
  • Week 1-2: Write 40-60 golden tasks (spec + tests) for web/ERP; benchmark 3-5 open models on them via vLLM with constrained decoding; record pass rate, latency, cost.
  • Week 2: Build the sandbox runner (Firecracker or gVisor) with no-egress policy and a package mirror; run 100 tasks through it.
  • Week 2-3: Stand up Temporal; implement the single-task harness loop (diagram 4) end-to-end for one task type (CRUD endpoint + tests).
  • Week 3: Implement Product + Architect agents with typed schemas (PRD, OpenAPI, DDL); build the approval inbox skeleton.
  • Week 4: Run the first end-to-end "idea to staging" on a small app at autonomy L0; review every trace; convert failures into new golden tasks.
  • Week 4: Decide with data: model mix, GPU tier to buy, which gates to keep manual; publish the Phase 1 plan and budget.
