Idea-as-a-Service: Low-Budget POC Plan

How to prove the core loop (idea to working, tested, deployed app) for $0 to about $900 instead of $300k+, and what to cut until it is proven.
Assumption. "IaaS" here means Idea-as-a-Service from your blueprint. It does not mean Infrastructure-as-a-Service. If you meant the latter, this plan needs to be redone.

1. What the POC must prove (and nothing else)

The full blueprint is a factory for ERP, web, mobile, IoT, network and cyber products. A POC should not build a factory. It should answer one question with evidence:

Can an AI pipeline, with a human approving three checkpoints, turn a one-page idea into a working, tested web app on a staging URL, at a cost and effort a small team could afford?

The narrow loop:

Idea (1 page) -> PRD + typed contracts (schema-validated) -> tests first -> code in sandbox
   -> verify (syntax, tests, lint, security scan) -> auto-repair (max 3 loops) -> staging URL
   Human gates: (1) approve PRD  (2) approve contracts  (3) approve staging build

In scope

  • One stack (recommended: FastAPI or Node + Postgres/SQLite + a simple React or server-rendered UI) and one demo domain (for example equipment rental or a small-business CRM).
  • A schema gate: every AI output that later steps depend on is validated against a typed schema before use.
  • A sandboxed build-and-test step and a bounded repair loop.
  • Cost and token tracking per project.

Explicitly out of scope

  • Mobile, IoT, network and cyber squads; compliance logic; multi-tenant billing; custom domains; maintenance automation; Kubernetes, Temporal, Firecracker, dedicated GPUs.

3. Design choices that keep it cheap

  • Template first, code second. Start with one hand-built, known-good app template (auth, CRUD, dashboard). Let the AI produce a validated specification and configuration plus targeted code for the parts that differ. This cuts tokens, failure rate and review effort sharply. Move to freer code generation only after the template path works.
  • One deployed app can host many configuration-driven "generated" apps (routes like /apps/<slug>). This avoids per-app infrastructure in the demo. It is a demo shortcut, not the final architecture.
  • Tests before code. Ask for tests from the contracts first. A failing test is a cheap, objective signal for the repair loop and for measuring quality.
  • Bounded loops. Max 3 repair attempts and a token budget per stage. When exceeded, stop and hand over to a human. Uncapped agents are the main way a low-budget POC turns into a high bill.
  • Model router. Every LLM call goes through one function that takes a role (plan, code, repair, review). Swap models per role without touching the pipeline.

8. This week's to-do list

  1. Choose the stack and the demo domain; write the three test ideas (easy, medium, hard).
  2. Install Docker and Ollama with one coder model; create one hosted-model API account with a hard monthly spend cap.
  3. Create the repo and Compose file; write the model router with two providers.
  4. Write the "project spec" schema (entities, fields, endpoints, acceptance criteria) and a validator.
  5. Build one hand-made template app and its test suite; this is the target the AI fills in.
  6. Get one stub run through all stages, logging tokens and cost.

9. After the POC

If the gate passes, follow the blueprint's roadmap in order: Tier A pilot infrastructure, Temporal for durable runs, Firecracker/gVisor for isolation, a second squad (for example ERP), and only then mobile, IoT, network and cyber. If it fails, the failure data tells you whether the problem is model quality, spec quality or verification, and each has a different fix.
